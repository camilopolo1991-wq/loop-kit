# ADR-002: the four hooks, by role, and the role variable

## Context

One hook cannot fit every role. A scout must write only into its own evidence folder, a writer must be kept off git and out of other goals, and a whole session must be kept from the shapes that leaked secrets. Four scripts live under `hooks/`. The three role hooks are second generation or newer, dated 2026-10-20 in their own headers.

## Decision

- `hooks/pretool-guard.py` is registered session-wide and covers every role.
- `hooks/readonly-guard.py` is registered in the frontmatter of the scout, the reviewer and the auditor. It reads the variable `LOOP_ROLE` from its command line: `scout` or `reviewer`. The role decides the evidence subfolder it may write (`T<nn>/` or `T<nn>/review/`). The auditor's file sets `LOOP_ROLE=reviewer`.
- `hooks/writer-git-guard.py` is registered on the writer's shell.
- `hooks/writer-path-guard.py` is registered on the writer's Write and Edit tools.

All four fail closed: an error inside a hook prints a deny and exits 0, and the agent files register them with `onFailure: block` and a timeout.

## Deliberately not

- Not one shared hook with a role switch inside it. A fault in one role's rules would then open every role.
- Not a role taken from the model's own say-so. The variable is set in the hook command line of the agent file.
- Not a promise of a sandbox. The writer's git hook is a net over a set of shapes tested by its rows, not over every shell construct.

## Consequences

- A new read-only role needs its own `LOOP_ROLE` value and a known evidence subfolder before it is registered.
- The writer's scope is the task branch worktree the leader lists in `writable.txt` and its own evidence folder, nothing else.
- A guard denial is quoted in the return and never respelled.

## Verification

```
tests/rows/C2/run.py <tree> <home> <work>
```

The rows feed the read-only hook one hook JSON each for a given role, and judge deny against allow. `tests/rows/C1/run.py` does the same for the writer's shell hook.
